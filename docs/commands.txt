START HERE

Run everything from the project root:

    cd <repo>/ymrl        e.g. D:\Documents\ymrl_root\ymrl

They are NOT under ymrl/tools/ unless you start one level up.


################################################################################
RULE: RE-EXPORT AFTER EVERY SOURCE CHANGE, BEFORE TRAINING
################################################################################

Training with --env_path runs build/YMRL.exe, and the export BAKES every .gd
and .tscn into the .pck. So:

    ANY change to a script or a scene INVALIDATES build/YMRL.exe.
    Re-export before the next --env_path training run, ALWAYS.

There is no warning if you forget. The build happily runs the old code, the
run looks normal, and the numbers reflect the settings you thought you had
replaced. This is the single easiest way to waste a training run in this
project.

    python tools/export_headless.py            # after every source change
    python tools/train_sb3.py --env_path build/YMRL.exe ...
    python tools/evaluate.py --model ... --env_path build/YMRL.exe ...

It nearly cost a run on 2026-11-20: build/YMRL.exe was exported with
TIME_COST_PER_STEP = 0.0 for the 5-zombie experiment, the constant was then
set back to 0.004, and the stale build was still sitting there. A --env_path
run at that point would have trained with the time cost silently off and
looked completely normal doing it.

Check before launching, rather than trusting memory -- if the source
timestamp is newer than the build, re-export (PowerShell):

    (Get-ChildItem -Recurse -Include *.gd,*.tscn characters,scenes,training |
        Sort-Object LastWriteTime -Descending | Select-Object -First 1).LastWriteTime
    (Get-Item build/YMRL.exe).LastWriteTime

EXCEPTION: in-editor training (no --env_path) reads .gd files straight off
disk, so it needs no export and cannot go stale. That is the reason to prefer
it while iterating on rewards or scenes; you give up --n_parallel, i.e. about
2.4x wall clock (see the SPEED section).

    python tools/train_sb3.py `
      --experiment_name soldier_finetune `
      --timesteps 60000 `
      --n_steps 256 `
      --ent_coef 0.001 `
      --linear_lr_schedule `
      --resume_model_path=models/soldier_5z_tc.zip `
      --save_model_path=models/soldier_next.zip `
      --onnx_export_path=models/soldier_next.onnx

No --env_path above, so this is in-editor training and needs NO export (see the
RULE at the top). Current task: 5 zombies (Training3Solo.tscn) with
TIME_COST_PER_STEP = 0.004. soldier_5z_tc is the best model on that task
(clears the wave in 38/50); soldier_tc_timecost is the best on the older
3-zombie task. See "Training results so far" below for the full comparison.


--- 2. TRAIN FROM SCRATCH ----------------------------------------------------

    python tools/train_sb3.py `
      --experiment_name soldier_scratch `
      --timesteps 200000 `
      --n_steps 256 `
      --ent_coef 0.01 `
      --save_model_path=models/soldier_scratch.zip

Use ent_coef 0.01 for a fresh run: that is what every from-scratch run in this
project used, and 0.001 has NOT been tested from scratch (it is not known to
fail there, just untested). For fine-tuning an existing checkpoint low entropy
is what stops it degrading -- see the results table below for the evidence.


--- 3. EVALUATE (do this before believing any training number) ---------------

    python tools/evaluate.py --model models/soldier_v10_50k.zip --episodes 50

50 episodes minimum. Four episodes gave 75% for a model that scores 42% at
n=50. Seeds are fixed, so runs are comparable.


================================================================================
CRITICAL: ORDER OF OPERATIONS (in-editor)
================================================================================

Start Python FIRST, then press PLAY:

    1. python tools/train_sb3.py ...     # blocks on "waiting for remote
                                         #  GODOT connection on port 11008"
    2. wait until this returns a row:
         Get-NetTCPConnection -LocalPort 11008 -State Listen
    3. press PLAY on training/Training3Solo.tscn

Startup takes 15-20 s (torch import + CUDA init). Poll for the listener; do not
sleep a fixed number of seconds and hope.

If the game starts before Python is listening it silently falls back to human
controls ("Couldn't connect to Python server") and Python dies on TimeoutError.
sync.gd now retries 30 times over ~15 s, but Python-first is still the reliable
order.

Also: project_run runs whatever scene the EDITOR HAS OPEN. If a probe left
soldier3.tscn or zombie3.tscn selected you will get a debugger break and no
connection. Confirm current_scene is training/Training3Solo.tscn first.


================================================================================
CRITICAL: WHAT CAN BE RUN WITHOUT THE TRAINING SERVER
================================================================================

The training scene needs a few lines of Python, NOT a special server program.
`tools/train_sb3.py` IS the server: it binds port 11008, waits for Godot, and
launches `build/YMRL.exe` itself. So you can drive the whole loop from one
shell, with no editor and no manual PLAY:

    python tools/train_sb3.py --env_path build/YMRL.exe --n_parallel 1 `
      --timesteps 512 --n_steps 256 --resume_model_path=models/soldier_5z_tc.zip

It prints "waiting for remote GODOT connection on port 11008", then "connection
established", then rollout stats. Verified working on 2026-11-21.

What CANNOT work is launching the training scene by itself with nothing
listening -- `Training3Solo.tscn`'s Sync node retries the connection 30 times
and then falls back to human controls, so `godot --path .` on that scene looks
like a hang. Only reach for that path when a trainer is already waiting (the
ORDER OF OPERATIONS section above).

To LOOK at the game (models, HUD, lighting, camera) without any trainer, run the
plain arena scene, which has no Sync node:

    godot --path . res://scenes/3d/main3.tscn

main3 defaults to 5 zombies; the training scene overrides the count.

ABOUT GPU (measured 2026-11-21 on this machine): an NVIDIA Quadro T1000 (4 GB)
is present. The venv originally had torch "+cpu", which silently disabled CUDA;
pyproject.toml now pins the cu128 index, giving torch 2.9.1+cu128. Check with:

    python -c "import torch; print(torch.__version__, torch.cuda.is_available())"

Do NOT use --n_parallel 1 with CUDA: enqueuing tiny tensors every env step costs
more than the CPU computes, so one env on GPU is SLOWER than CPU
(44-48 fps vs 63-65). Parallel envs amortise that overhead:

    n_parallel 1  CPU 63-65 fps ... GPU 44-48 fps   (GPU loses)
    n_parallel 2  GPU 76-81 fps
    n_parallel 4  GPU 119-127 fps   <- USE THIS

50k steps at ~120 fps is roughly 7 minutes.

At 5 zombies kill_rate (>=1 kill) is no longer informative -- read kills/ep and
"cleared the wave" instead. The 64% row predates the soft-collision change and
is NOT comparable to the rows above it. Everything else was measured on the
current physics at n=50, deterministic, same seeds.

WHICH SCENE each model was measured on: v10/v11/soldier_tc at 3 zombies (what
Training3Solo.tscn had then), soldier_5z and soldier_5z_tc at 5 zombies. The
scene is now set to 5 AND TIME_COST_PER_STEP is 0.004, so re-running an old
eval now measures a different task/reward than it did originally.

TIME COST vs 5 ZOMBIES: three fine-tunes, n=50

    metric             v11(3z)  A: time   B: 5z   C: 5z+time
    return_              34.68     34.49    45.32      52.89
      (penalty-free)     34.68     ~35.7    45.32      ~54.6   <- comparable column
    kills/ep           2.92/3    2.98/3   3.76/5     4.76/5
    cleared the wave     46/50     48/50     6/50      38/50
    length                 315       296      453        426   (cap ~456)
    idle_fraction         0.21      0.10     0.02       0.01
    attack_fraction       0.57      0.68     0.63       0.77
    damage_taken          0.77      0.48     1.02       3.02
    deaths/ep             0.00      0.00     0.00       0.00

  A (time cost, 3 zombies): fixed the loitering it was aimed at -- idle halved,
  attacks up, episodes 19 steps shorter, damage DOWN. Kept as the default.

  B (5 zombies, no time cost): harder scene kills loitering by itself (idle
  0.02, nothing to linger for), but it cannot convert: 3.76 of 5 kills, 44/50
  episodes hit the 60 s cap. That was the headroom.

  C (5 zombies + time cost, 60k from soldier_5z) is the win: clears the wave in
  38/50 instead of 6/50, kills 4.76 of 5 instead of 3.76, in 27 fewer steps,
  with attack_fraction 0.77. The price is explicit and intended -- damage taken
  1.02 -> 3.02, still zero deaths. That is the time cost buying engagement, on
  a scene where engagement was the binding constraint.

  Read C's damage number as the design intent, not a regression: A and C differ
  because on 3 zombies there is spare time to spend, on 5 there is not.

3 vs 5 ZOMBIES
  Training3Solo.tscn overrides zombies_per_episode; main_3.gd defaults to 5.
  At 3 the task is saturated (kill_rate pinned at 100%, kills/ep 2.92 of 3), so
  only the damage/time terms have room and training just trades speed for
  safety. At 5 there is real headroom. The obs sensor already has 10 slots, so
  5 zombies needs no shape change and old checkpoints still load.

Do NOT nerf strafe/backpedal to punish circling. char3.gd sets STRAFE_SPEED =
BACKPEDAL_SPEED = 0.75, so slowing one slows the other -- it cannot
"incentivize retreating", it just weakens both. Retreat is already dominated: a
wounded zombie runs at 4.0 vs the soldier's 2.25 backwards, and retreating into
a 50x50 arena's walls is the wedge failure the soft collision fixed. The
behaviour is legitimate kiting of the 0.4 s attack_startup freeze, and it can
also be done with forward + turn at full speed, so a strafe nerf would be
routed around anyway. Price time (as in A and C) if you want decisiveness.

What the v10 run established:

  The soft-collision change is worth more than the training. Both models scored
  on identical physics, n=50:
      model                    kill_rate  kills/ep  return  dmg_taken  attack_frac
      soldier_best_64pct (v9)      88%      1.28     6.05       7.09         0.14
      soldier_v10_50k              100%      2.92    32.28       2.36         0.49
  So 64% -> 88% is the physics alone (a policy that never saw it), and
  88% -> 100% plus kills/ep 1.28 -> 2.92 is what the 50k fine-tune added.
  v10 also stops being passive: attack_fraction 0.14 -> 0.49 and
  block_fraction 0.25 -> 0.10 -- the old policy spent its time blocking and
  timing out at the 450-step cap; v10 kills all three zombies and ends via the
  all-zombies-killed condition (mean episode length 268 vs 435).
  Caveat: the cap is 3 zombies per episode, so kill_rate is at ceiling and
  kills/ep has almost no room left. Further fine-tuning needs a harder scene
  (more zombies) to show anything.

  Reproduce with:
      python tools/evaluate.py --model models/soldier_v10_50k.zip --episodes 50 \
        --json eval_v10_50k.json
      python tools/evaluate.py --model models/soldier_best_64pct.zip --episodes 50 \
        --json eval_best64_soft_n50.json

  Training run itself: 50,176 steps in 732 s (~68 fps), stochastic
  success_rate 0.98, ep_rew_mean 20.5 -> 30.8. Checkpoints were written every
  10k; the 10k-30k files have been pruned, so
  logs/sb3/soldier_v10_50k_checkpoints/ now holds only the 40k and 50k pair
  (the 50k one duplicates models/soldier_v10_50k.zip, which was also saved
  after the run finished, and is the file to resume from).

What earlier runs established:

  ent_coef is the dominant setting when fine-tuning. Two 20k runs from the
  same 42% baseline, differing ONLY in ent_coef:
      ent_coef 0.01  -> declined every step, ended at 12%
      ent_coef 0.001 -> held 61-71%, evaluated 64%
  High entropy pressure dismantles a policy that has already converged.

  LR decay must have a floor. Decaying to 0 froze the policy at ~1.8e-06 and
  it could not recover from a dip (peaked 86%, fell to 64%). Now decays to
  10% of initial (LR_FLOOR_FRACTION in train_sb3.py).

  Evaluation beats training logs. Training's success_rate is measured on a
  STOCHASTIC policy; evaluate.py uses argmax. They are not comparable, and the
  rolling-window numbers were consistently more optimistic than reality.


================================================================================
ENVIRONMENT
================================================================================

Shapes (train_sb3.py asserts these at startup; a mismatch exits with a message)
    observation: 103 floats
        8   wall rays     (WallSensor, walls only)
        90  entity slots  (EntitySensor: 10 slots x 9 values per enemy)
        5   manual        (health, stamina, x, z, yaw)
    actions: MultiDiscrete([9, 3, 2, 2, 2]) -- alphabetical, see below
        attack (2), block (2), move (9), sprint (2), turn (3)

    Checkpoints saved under a different shape are NOT loadable. A tensor-shape
    crash from PPO.load means this, not a corrupt file.

    The action keys in soldier3_ai.gd::get_action_space() are declared
    ALPHABETICALLY on purpose. Godot's JSON.stringify sorts keys but
    sync.gd::_extract_action_dict slices by insertion order; if those disagree
    every action goes to the wrong head, silently. Do not reorder them.

Scene and mechanics
    Arena: scenes/3d/main3.tscn -- 50x50, 60 s episodes.
    training/Training3Solo.tscn overrides some values; the scene wins.

    Zombies: training/Training3Solo.tscn sets zombies_per_episode = 3. Note the
    script default in main_3.gd is 5 -- the scene override is what training uses.

    Zombies walk at 2.0 and run at 4.0 once below half health.
    They freeze during their 0.4 s attack wind-up, so backing off can escape.

    Soldier speed_stat is the Char3 default of 3.0. It is only read in
    soldier3.gd (line 161), never assigned, and the scene does not set it.

Episode ends on: soldier death, EpisodeTimer (60 s), or all zombies killed.
All three set `done`, which is what makes info["episode"] appear.


================================================================================
HYPERPARAMETERS: WHAT THE FLAGS DO
================================================================================

Applied on resume only:
    --learning_rate   (with --linear_lr_schedule)
    --ent_coef
Everything else is restored from the checkpoint and IGNORED on resume:
    --n_steps, --batch_size, --gamma, --clip_range, --n_epochs

    The script prints "Resumed config (...)" -- read it, it shows what is
    actually in effect.

NOT command-line flags at all:
    gamma = 0.995 is hardcoded in the PPO(...) call. There is no --gamma flag
    and parse_known_args() silently swallows one if you pass it.
    SHAPING_GAMMA in soldier3_ai.gd MUST equal it, or the potential-based
    reward shaping loses its policy-invariance guarantee. Change both together.

    --batch_size defaults to the full rollout (n_steps x n_envs) and must
    divide it evenly; a non-divisor is rejected with an explicit error.

    --device defaults to "auto" (CUDA when available).

    --n_parallel > 1 requires --env_path; each parallel env is a separate
    Godot process, so in-editor training cannot be parallelized.

Reward design
    Shaping is potential-based (F = gamma*phi(s') - phi(s), phi = -distance).
    Do NOT replace it with a raw per-metre reward -- that pays for approaching
    without charging for retreating and the agent learns to oscillate.

    Zombies spawn at a random distance in [3, 22] m, a deliberate curriculum
    giving short and long credit-assignment problems in the same run.

    HURT_PENALTY_FACTOR 5.0 (0.125 per zombie hit, ~80 hits per kill). At 1.0
    damage was free; at 20.0 the damage term drowned the kill signal with
    multiple zombies.

    Blocking is charged 0.004 per step held, on top of the 0.05 press cost.
    Without the per-step charge a policy held block 100% of the time and farmed
    the block reward while never attacking.


================================================================================
SPEED: WHAT ACTUALLY MAKES TRAINING FASTER (measured 2026-11-20)
================================================================================

Use the exported build with 4 parallel envs. Everything else is noise:

    # STEP 0, NOT OPTIONAL: re-export first if ANY .gd/.tscn changed since the
    # last export. --env_path runs the baked build, so skipping this trains on
    # old code with no warning. See the RULE at the top of this file.
    python tools/export_headless.py

    python tools/train_sb3.py `
      --experiment_name soldier_v12 `
      --env_path build/YMRL.exe --n_parallel 4 --speedup 30 --fixed_fps 2000 `
      --timesteps 60000 --n_steps 256 --ent_coef 0.001 --linear_lr_schedule `
      --save_checkpoint_frequency 15000 `
      --resume_model_path=models/soldier_5z_tc.zip `
      --save_model_path=models/soldier_v12.zip --onnx_export_path=models/soldier_v12.onnx

Measured, same config, 4k-9k step runs (i7-9700K, 8 threads / 8 logical):

    setup                                              env steps/s
    in-editor, windowed, scene speed_up 10                     68   <- previous runs
    in-editor, --headless --fixed-fps 2000, --speedup=30        79
    ... + --device cpu                                          83
    exported build, single env (any flags)                      50
    exported build, --n_parallel 4                              167
    exported build, --n_parallel 4 --speedup 30 --fixed_fps 2000 256  <- USE THIS
    exported build, --n_parallel 6 --speedup 30 --fixed_fps 2000 218  (oversubscribed)

    50k steps: measured on real runs, 12.2 min in-editor (v10) -> 5.1 min with
    n_parallel 4 (v11), i.e. ~2.4x. The 256 steps/s above is a short-run
    benchmark; long runs settle lower (v11 162, and 119 on 5 zombies) once
    checkpoint writes and longer episodes are included. Do not budget from 256.

The last two flags are worth 167 -> 256 in parallel mode, even though neither
helped a single-env build. --n_parallel 4 beats 6 because 4 Godot processes +
Python + the OS already fill 8 threads; retune if the machine changes.

WHY THE EXPORT EXISTS: it does NOT make one env faster -- the exported build is
SLOWER per env than the editor binary (50 vs 68-83). Its only real benefit is
that godot_rl refuses --n_parallel > 1 without --env_path, so the export is
what unlocks the 4 processes. Net effect is ~2.4x wall clock (162-256 aggregate
vs 68-83 single), and nothing more.

Training in-editor instead (no export) is a legitimate choice: it reads .gd
files straight off disk, so the stale-build trap in the RULE at the top simply
cannot happen -- at the cost of that 2.4x. Concrete: soldier_5z_tc (60k steps,
5 zombies) took 18.5 min in-editor at 54-70 steps/s; at 4 parallel envs the
same 60k was an estimated 5-7 min.

Re-exporting is the price of the 2.4x. There is no third option that keeps both.

What did NOT work (do not re-spend the effort):

  Throttling the soft-separation shape query in char3.gd to every 2nd or 8th
  tick: 79 / 79 / 80 fps at interval 1 / 2 / 8. The query is not the cost.
  Reverted; the reason is recorded in char3.gd so it is not "optimised" again.

  Engine.max_physics_steps_per_frame (default 8) clamps speed_up above 8, so
  training.gd raises it to 64. Throughput did not change (52 -> 50 fps): frames
  just get proportionally longer. Kept only so speed_up means what it says.

  Passing --fixed_fps to the build (new --fixed_fps flag): no change, 50 -> 50.

  --device cpu and --speedup only pay off in-editor; the exported build sits at
  ~50 env steps/s single-env regardless. Why the build is slower than the
  editor binary at the same speedup is UNRESOLVED -- it is not the frame cap,
  not --fixed-fps, and not rendering (--headless). Parallelism hides it, which
  is why it was parked rather than chased.

  Not worth trying: swapping SB3's PPO for CleanRL (same algorithm; the env is
  a Godot process behind a blocking socket, so CleanRL keeps the same
  bottleneck) and SAC (sample-efficient in principle, but SB3's SAC rejects
  MultiDiscrete -- see below -- and the task is at a 100% ceiling).

Two tool bugs found and fixed while setting this up:

  tools/export_headless.py built its template URL from GODOT_VERSION
  ("4.7.2.stable") but GitHub release tags use a hyphen ("4.7.2-stable"), so
  --install-templates 404'd on all 5 retries. Fixed; templates now install.

  tools/train_sb3.py defaulted --speedup to 1 and unconditionally passed it to
  the env. godot_rl forwards it to the launched build, overriding the scene's
  speed_up=10, so every --env_path run crawled at 6 env steps/s. Now defaults
  to None (= use the scene's value).

  Note: --n_parallel is the ONLY thing that needs --env_path; in-editor runs
  cannot be parallelised. Export needs ~1.2 GB of templates once, and
  --export-release can be run straight from the editor binary even while the
  editor is open (the tool's "close the editor first" guard is over-cautious
  and also misfires on the godot-ai MCP server, whose pid-file path contains
  "YMRL"):

    GODOT_BIN=".../Godot_v4.7.2-stable_mono_win64_console.exe" `
      ".../Godot_v4.7.2-stable_mono_win64_console.exe" --headless `
      --path . --export-release "Headless" build/YMRL.exe
